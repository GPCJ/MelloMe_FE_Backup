## 배경

R-08 4단계는 "PostListPage 토글 후 뒤로가기 시 PostCard 재마운트가 stale RQ 캐시에서 옛 값으로 회귀하는 버그" fix입니다. PUT 응답으로 hook 내부 state는 reconcile되지만 RQ `useInfiniteQuery` 캐시(`['feed', {size}]`)는 그대로라, 카드 재마운트 시 거기서 옛 값을 다시 받습니다.

핵심 작업은 "RQ 캐시도 같이 갱신"인데, 이 갱신 책임을 어디에 둘지 3가지를 검토했습니다.

## 검토한 3가지 옵션

### A — hook이 직접 캐시 패치
`useReactionToggle` 안에서 RQ queryClient를 직접 들여와 캐시를 갱신합니다.

매력: 호출부가 0개 영향. 새 화면에서 PostCard를 써도 자동으로 캐시 패치가 따라옵니다.
비용: hook이 "리액션 토글"과 "feed 캐시 갱신" 두 책임을 짊. hook이 RQ에 결합됩니다.

### B — hook은 신호만 위로, 페이지가 캐시 패치 (채택)
hook이 PUT 응답을 받으면 옵션 콜백으로 부모에 신호를 올리고, 부모(PostListPage)가 자기 캐시를 직접 패치합니다.

매력: hook이 RQ를 모름(추상화 깨끗). 댓글 리액션 hook의 B 패턴(페이지가 진실 보유)과 같은 컨벤션.
비용: 새 호출부마다 콜백 등록을 의식적으로 해야 함. 등록 누락 시 그 화면에서 같은 stale 회귀 버그 재발.

### C — 단순 invalidate
캐시를 stale 표시만 하고 다음 마운트 때 백엔드에서 feed를 통째로 다시 받습니다.

매력: 코드가 1줄로 가장 짧음.
비용: 토글 직후 새 데이터 도착 전까지 잠깐 옛 값 노출(퇴화 깜빡임). 네트워크 1회 추가.

## 결정 = B (Why)

댓글 리액션 hook이 이미 B 패턴(페이지가 comments 배열 단일 진실로 보유, hook은 setComments 콜백으로 갱신)으로 채택된 컨벤션과 일관성을 유지하기 위함입니다. 게시글 리액션도 같은 형태로 통일하는 것이 R-08의 더 큰 그림이기도 합니다.

A는 코드는 약간 짧지만 hook의 추상화 책임이 늘고, C는 깜빡임 비용이 사용자에게 보입니다.

## 한계점 (B 채택 비용 박제)

새 호출부에서 PostCard를 사용할 때 `onReactionUpdated` 콜백 등록을 잊으면 같은 stale 회귀 버그가 재발합니다. 호출부 추가 시 체크 필요합니다.

## 보충

헬퍼 함수(`patchPostInFeed(qc, fresh)`)로 캐시 순회 로직을 추출하면 A/B/C 3옵션의 호출 위치 코드 길이가 거의 같아집니다(1줄). 즉 진짜 트레이드오프는 코드 길이가 아니라 "기본 동작이 캐시 갱신 ON(A)이냐, 호출부가 의식적으로 ON시켜야 하나(B)냐, 깜빡임 감수(C)냐"입니다.
