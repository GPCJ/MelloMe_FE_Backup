## [TIL] 전역 모달의 두 가지 마운트 전략 — 조건부 마운트 vs 상시 마운트 + return null

> 분류: TIL
> 맥락: 쪽지(DM) 작성 모달(`MessageComposeModal`)을 구현하며, 여러 진입점이 하나의 모달을 공유하는 구조를 학습했습니다.

### 문제 상황

쪽지 작성 모달은 진입점이 여럿입니다. 게시글 상세의 작성자 프사, 댓글 N개의 프사 등 어디서든 "쪽지 보내기"를 누르면 같은 모달이 떠야 합니다. 진입점마다 모달 인스턴스를 두면 복잡해지므로, 전역 store(Zustand)를 **접수대**처럼 두고 모든 진입점이 그 store에만 말을 거는 구조를 택했습니다.

- store가 들고 있는 것: `open`(열림 여부), `receiverId`, `receiverNickname` — 즉 "열렸나 / 누구한테"만.
- 쪽지 본문(`content`)은 store가 아니라 모달의 로컬 `useState`에 둡니다. 여러 진입점이 공유할 필요가 없는 임시값이기 때문입니다.
- 진입점 → `openCompose({ id, nickname })` 호출 → store state 변경 → store를 구독하던 모달이 반응.

### 핵심 학습 — 모달을 "숨기는" 세 가지 방식

1. **조건부 마운트**: 부모가 `{open && <Modal/>}`로 그림. 닫으면 컴포넌트가 **언마운트**되고 로컬 state도 자동 소멸.
2. **상시 마운트 + return null**: 컴포넌트는 늘 살아있고, 닫혔을 때 `return null`로 **아무 DOM도 안 그림**. ← 이 모달이 택한 방식.
3. **display:none**: DOM 노드는 계속 존재하고 CSS로 시각만 숨김.

2번에서 헷갈리기 쉬운 점: "상시 마운트"라고 닫힌 모달이 DOM에 숨어있는 게 아닙니다(3번 아님). `return null`이라 닫히면 모달 마크업 DOM은 **아예 존재하지 않습니다**. 다만 **컴포넌트 함수(fiber) 자체는 늘 마운트**돼 있어서, 그 안의 로컬 state(`content`)는 닫혀도 **살아남습니다**.

- 거주자(컴포넌트 인스턴스 + state) = 안 나감 (상시)
- 거주자가 만든 가구(DOM) = 닫히면 치움(null), 열리면 다시 만듦

### 따라오는 대가 — 수동 청소

조건부 마운트(1번)는 언마운트 시 React가 로컬 state를 자동으로 비워줍니다. 하지만 상시 마운트(2번)는 컴포넌트가 안 나가므로 `content`가 그대로 남습니다. A에게 쓰다 닫고 B에게 다시 열면 A에게 쓰던 글이 남는 사고가 납니다. 그래서 `useEffect`로 `open`이 false가 될 때 `content`를 손수 리셋해야 합니다. store의 `receiverId`도 닫을 때 null로 비워야 다음 진입에 잔상이 안 남습니다.

### 트레이드오프 — 솔직한 평가

직관적으로는 **조건부 마운트가 더 간단합니다**(자동 청소, 수동 리셋 불필요). 상시 마운트가 실제로 유리한 경우는 좁습니다:

- 닫힘 애니메이션(fade-out 동안 엘리먼트가 잠시 남아야 함)
- 열고 닫아도 입력값/스크롤/포커스를 보존하고 싶을 때
- 마운트 비용이 큰 무거운 콘텐츠

이 쪽지 모달은 위 어느 것도 강하게 해당되지 않습니다. 상시 마운트를 택한 실제 이유는 **프로젝트의 기존 `PostWriteModal`이 같은 패턴이라 일관성을 맞춘 것**입니다. 기능상 조건부 마운트도 충분히 정당한 선택이었고, 오히려 더 단순했을 수 있습니다. 패턴 일관성과 단순성 사이의 트레이드오프를 명확히 인지하는 것이 학습 포인트입니다.

### 상시 마운트의 장점

1. **Layout이 깔끔해집니다.** Layout은 `<Modal/>` 한 줄만 두면 되고, open 상태를 구독·게이트할 필요가 없습니다. 모달이 자기 상태를 자기가 책임지는 완전 캡슐화입니다.
2. **트리거와 모달이 완전히 분리됩니다.** 모달이 항상 트리에 대기하므로, 어느 진입점이 store를 켜든 마운트 타이밍 걱정 없이 즉시 반응합니다. "모달이 아직 안 그려졌으면?" 같은 race가 원천 봉쇄됩니다.
3. **열고 닫을 때 재구성 비용이 없습니다.** 첫 마운트 한 번이면 끝이고 이후엔 토글만 합니다. 내부 effect·구독·포커스 트랩이 매번 설치/해제되지 않습니다.
4. **닫힘 애니메이션이 가능합니다.** 엘리먼트가 트리에 남아있어 fade-out 같은 exit 트랜지션을 줄 수 있습니다. 조건부 마운트는 언마운트 즉시 사라져 불가능합니다.
5. **작성 중 내용을 살려둘 수 있습니다.** 닫았다 다시 열어도 입력값·스크롤·포커스를 이어가는 임시저장 UX를 별도 저장소 없이 로컬 state만으로 얻을 수 있습니다.
6. **코드베이스 일관성.** 프로젝트의 모든 전역 모달이 같은 패턴이라 한 번 익히면 어느 모달이든 똑같이 읽힙니다.

### 상시 마운트의 단점

1. **수동 청소 의무가 생깁니다.** 닫혀도 언마운트되지 않아 로컬 state가 살아남으므로, `useEffect`로 손수 리셋해야 합니다(`MessageComposeModal.tsx:20-22`의 content 리셋). 빠뜨리면 다음 진입에 이전 입력이 새는 잔상 버그가 납니다.
2. **라우트를 옮겨도 안 닫힙니다.** open이 전역 store에 살아있어 navigate만으로는 닫히지 않으므로, 강제 close effect를 추가해야 합니다(`PostWriteModal.tsx:21-26`).
3. **상시 비용이 미세하게 존재합니다.** 닫혀있어도 컴포넌트 함수는 부모 리렌더마다 호출되고 store 구독도 유지됩니다. `return null`이라 DOM은 없지만 fiber와 구독은 살아있습니다.
4. **공유 인스턴스의 state 누수 위험.** 여러 진입점이 단일 모달 인스턴스를 공유하므로, 한 곳에서 남긴 state가 청소되지 않으면 다른 진입점에서 열 때 새어나옵니다.
5. **"fresh 시작"이 공짜가 아닙니다.** 조건부 마운트는 매번 깨끗한 초기 상태로 시작하는 게 기본값인데, 상시 마운트는 그 초기화를 명시적으로 구현해야 합니다.
6. **추론 비용이 한 겹 늘어납니다.** "닫혀있는데 왜 이 컴포넌트가 트리에 있지?", "이 리셋 effect는 왜 필요하지?"를 이해해야 코드가 읽힙니다. 신규 합류자에게 진입 장벽이 됩니다.

### 정리

장점 1~3, 6은 이 쪽지 모달에 **실제로 적용되는 이점**이고, 4~5(애니메이션·내용 보존)는 **지금은 안 쓰지만 열려있는 잠재 이점**입니다. 단점은 대부분 "수동 청소 의무"로 수렴합니다. 결국 **"Layout 단순화 + race 봉쇄 + 일관성"을 얻는 대가로 "닫힐 때 손수 비우는 코드"를 떠안는** 거래입니다.

### 최종 의사결정 — 이 쪽지 모달은 조건부 마운트로 전환

장점·단점을 모두 나열한 뒤, **이 쪽지 작성 모달에 한해 조건부 마운트로 전환**하기로 결정했습니다.

**판단 근거:**
- 상시 마운트가 사주는 이점(깜빡임 없음·닫힘 애니메이션·작성 내용 임시저장) 중 **이 모달에서 실제로 활용되는 것이 하나도 없습니다.** 닫힘 애니메이션은 미구현, 임시저장은 오히려 매번 비우길 원함, 모달이 가벼워 재마운트 비용은 체감 0입니다.
- 즉 **복잡도(수동 청소 useEffect)를 떠안았는데, 그 복잡도가 사주는 퍼포먼스가 없습니다.** 복잡도가 높더라도 그걸 활용해 성능/UX 이득이 나오면 정당하지만, 이 경우는 아닙니다.

**조건부 마운트 전환으로 잃는 것(단점 = 포기하는 상시 마운트 이점):**
1. 닫힘 애니메이션을 줄 여지 — 단 현재 미사용이라 실손실 없음.
2. 작성 중 내용을 살려두는 임시저장 UX 여지 — 단 현재 의도적으로 안 씀이라 실손실 없음.
3. 모달 열고 닫을 때 재마운트가 발생 — 단 가벼운 모달이라 비용 무시 가능.
4. 코드베이스 일관성 한 줄 깨짐 — 기존 `PostWriteModal`은 상시 마운트인데 이 모달만 조건부가 됨. → 이건 **백로그로 남겨** 추후 `PostWriteModal`도 같은 판단으로 전환할지 별도 검토.

**구현 방식 — 얇은 게이트 컴포넌트(조건부 B):**
- 단순히 Layout이 `open`을 구독해 `{open && <Modal/>}`로 게이트하면(조건부 A), 수동 청소 비용은 없애지만 **모달 열 때마다 Layout 아래 현재 페이지 전체가 리렌더되는** 새 비용이 생깁니다.
- 그래서 state 없는 얇은 게이트 컴포넌트(`MessageComposeModalGate`)가 `open`만 구독해 모달을 조건부로 그리게 합니다. → Layout은 단순 유지, 리렌더는 게이트+모달로 좁게 격리, content는 언마운트로 자동 청소. 대가는 작은 파일 1개.

**스코프 규율:** 기존 `PostWriteModal`(상시 마운트)은 **이번에 건드리지 않고 백로그**로 둡니다. 이번 작업은 쪽지 모달만 조건부 마운트로 전환합니다.

## [TIL] 진입점이 여럿인 분기 로직을 hook 한 곳에 가두기 — "중복 제거"의 본질

> 분류: TIL
> 맥락: 쪽지 작성은 PC에서는 모달, 모바일에서는 라우트로 진입합니다(CH-09 정책). 이 분기를 `useOpenMessageCompose` hook 한 곳에 모았습니다.

### 분기의 실체

쪽지 작성 진입점은 게시글 상세, 댓글 등 여러 곳이고, 어디서 눌러도 화면 폭에 따라 동작이 갈립니다.

- PC(`min-width: 768px`): 전역 store로 모달을 토글합니다(`openCompose(receiver)`).
- 모바일: `/messages/new?to=...&name=...` 라우트로 navigate합니다.

이 `matchMedia` 분기를 `useOpenMessageCompose.ts` 하나에 넣고, 모든 진입점은 이 hook이 돌려주는 `open(receiver)` 함수만 호출합니다.

### 핵심 학습 — "중복 코드가 안 생긴다"의 한 단계 아래

처음 떠올린 이유는 "hook으로 모듈화하면 중복 코드가 안 생긴다"였습니다. 맞지만 이건 **결과**고, 그 중복이 **왜 나쁜지**가 진짜 이득입니다. 이 hook이 가둔 것은 코드 줄 수가 아니라 **"PC=모달 / 모바일=라우트"라는 정책 그 자체**입니다. 그래서 이득이 두 갈래로 나뉩니다.

**① 정책 변경 시 한 곳만 고칩니다 (single source of truth).**
분기 기준 breakpoint(768), 모바일 경로(`/messages/new`)가 나중에 바뀔 수 있습니다. breakpoint를 1024로 올리거나, 경로를 바꾸거나, "PC도 라우트로 통일"로 정책이 뒤집히면 — hook이 없으면 모든 진입점을 일일이 찾아 고쳐야 하고, 진입점은 앞으로 더 늘어납니다. hook이 있으면 `useOpenMessageCompose.ts` 한 줄만 고치면 끝입니다.

**② 진입점 간 동작 불일치(divergence)를 막습니다.**
중복 코드의 진짜 위험은 양이 많은 게 아니라 **복사본들이 서로 어긋나는 것**입니다. 한 진입점은 768, 다른 곳은 실수로 767을 쓰거나, 한쪽만 `encodeURIComponent`를 빠뜨리면 같은 "쪽지 쓰기"가 화면마다 다르게 동작합니다. 단일 통로면 모든 진입점이 무조건 똑같이 동작합니다.

### 정리

"중복 제거"는 표면이고, 그 본질은 **정책의 단일 출처 + 진입점 동작 통일**입니다. 분기 로직을 hook에 가두는 판단의 기준은 "줄이 중복되나?"가 아니라 **"이게 한 곳에서만 결정돼야 하는 정책인가?"**입니다.

## [트러블슈팅] 쪽지 작성 모달 검증 중 발견한 3가지 문제 — 스크롤 잠김 / 토스트 중복 / 라우트 이동 시 토스트

> 분류: 트러블슈팅
> 맥락: 쪽지(DM) 작성 기능을 브라우저에서 검증하던 중 세 가지 문제를 발견해 수정했습니다. 세 건 모두 전역으로 공유되는 자원(body 스크롤, 토스트 큐)을 누가 어떻게 다루느냐가 핵심이었습니다.

### 1. 드롭다운이 잠근 스크롤이 모달을 통해 누수된 문제

**증상**

작성자 프사 드롭다운에서 쪽지 모달을 열었다 닫은 뒤 다른 페이지로 이동하면 스크롤이 동작하지 않았습니다. DevTools로 보면 `<body>`에 `overflow: hidden`이 남아 고정돼 있었습니다. 반면 드롭다운만 열고 프로필·팔로우(토스트만 뜨는 항목)를 누른 경우에는 스크롤이 정상이었습니다.

**공유 자원**

`document.body.style.overflow` 하나를 드롭다운과 쪽지 모달이 함께 건드립니다.

- 드롭다운(Base UI)은 `modal` 기본값이 `true`라, 열릴 때 body를 `overflow: hidden`으로 잠급니다.
- 쪽지 모달(`MessageComposeModal.tsx:24-28`)은 "열 때 body의 현재값을 메모 → hidden으로 설정 → 닫을 때 메모한 값으로 복원" 패턴을 씁니다.

**원인**

모달이 메모를 뜨는 타이밍에 body가 이미 hidden이었던 것이 문제였습니다.

1. 드롭다운이 열리며 body를 hidden으로 잠급니다.
2. 그 상태에서 쪽지 모달이 열리며 "원래값"을 메모하는데, 이미 hidden이라 잠긴 값을 원래값으로 잘못 기록합니다.
3. 드롭다운이 닫히며 자기 메모대로 정상 복원합니다(여기까진 멀쩡).
4. 모달이 닫히며 자기 메모(hidden)대로 복원해 body가 hidden으로 박제됩니다.

즉 드롭다운은 자기 뒷정리를 정상적으로 합니다(그래서 프로필·팔로우만 누르면 스크롤이 멀쩡합니다). 누수가 터지는 장소는 모달이지만, 모달이 잘못된 값을 메모하게 만든 조건은 드롭다운의 스크롤 락이었습니다.

**왜 모달이 아니라 드롭다운을 고쳤나**

모달의 "메모하고 복원하는" 패턴 자체는 버그가 아니라 올바른 관용구입니다. 같은 패턴을 쓰는 `PostWriteModal`, `CommentReplyModal`은 멀쩡한데, 그 둘은 버튼에서 직접 열려 열리는 순간 body가 깨끗하기 때문입니다. 쪽지 모달만 유일하게 이미 잠긴 드롭다운 안에서 열려 더러운 값을 메모했습니다.

여기서 모달을 특수 케이스로 고치면(닫을 때 무조건 빈 값으로 복원 등) 세 모달 중 쪽지 모달만 복원 방식이 달라져 일관성이 깨지고 읽기 어려워집니다. 대신 유일한 비정상(작은 액션 메뉴가 굳이 스크롤을 잠그던 것)을 제거하는 쪽을 택했습니다.

**수정**

`UserActionDropdown.tsx:33`의 `<DropdownMenu>`를 `<DropdownMenu modal={false}>`로 바꿔 드롭다운의 스크롤 락을 껐습니다. 그러면 모달이 열릴 때 body가 깨끗한 상태라 올바른 값을 메모하고, 닫을 때 정상 복원됩니다. 3개짜리 작은 메뉴라 배경 스크롤을 잠글 이유도 없어 UX 손해도 없습니다.

### 2. 같은 안내 토스트가 클릭마다 쌓인 문제

**증상**

드롭다운의 프로필·팔로우(준비 중 기능)를 누르면 "준비 중인 기능이에요" 토스트가 뜨는데, 연타하거나 두 항목을 번갈아 누르면 같은 토스트가 화면에 여러 개 쌓였습니다.

**공유 자원**

앱의 토스트는 전부 `main.tsx:24`의 단일 `<Toaster>` 큐를 통해 렌더됩니다. 어디서 `toast(...)`를 부르든 같은 큐에 들어갑니다.

**원인**

`toast('준비 중인 기능이에요')`처럼 `id` 없이 호출하면, sonner는 호출할 때마다 **새 토스트를 큐에 추가**합니다. 클릭 횟수만큼 별개의 토스트가 생겨 쌓입니다.

**수정**

`UserActionDropdown.tsx:39,45`의 두 호출에 동일한 `id`를 부여했습니다.

```
toast('준비 중인 기능이에요', { id: 'coming-soon' })
```

sonner는 `id`를 토스트의 신원(key)으로 봅니다. 호출은 매번 받되, 그 `id`를 가진 토스트가 이미 떠 있으면 **새로 만들지 않고 기존 것을 갱신**(내용·타이머 리셋)합니다. 즉 함수 호출을 막는 게 아니라, 라이브러리 내부의 중복 처리(dedup)를 활용한 것입니다.

프로필·팔로우 두 항목이 같은 `id`('coming-soon')를 쓰므로, 무엇을 몇 번 누르든 화면에는 항상 토스트 하나만 유지됩니다(둘 다 텍스트도 동일).

### 3. 페이지를 이동해도 토스트가 남아있던 문제

**증상**

준비 중 안내 토스트가 떠 있는 상태에서 다른 페이지로 이동해도 토스트가 닫히지 않고 남아 있었습니다. 페이지를 옮기면 자연스럽게 사라지길 원했습니다.

**원인**

토스트는 시간이 지나면 자동으로 닫히지만, 라우트 전환과는 연결돼 있지 않았습니다. 이동 시 닫으려면 "라우트가 바뀌는 순간"을 감지해 토스트를 닫아주는 코드가 따로 필요했습니다. 코드베이스에는 그런 패턴이 없었습니다(`PostWriteForm`의 `toast.dismiss()`는 수동 호출이라 라우트 기반이 아님).

**수정**

`Layout.tsx`에 다음 effect를 추가했습니다.

```
useEffect(() => {
  toast.dismiss();
}, [location.pathname]);
```

동작 원리는 useEffect 의존성 규칙입니다. React는 리렌더마다 의존성 배열의 값을 이전 값과 비교하고, 달라졌을 때만 effect를 다시 실행합니다. 페이지를 이동하면 `location.pathname`이 바뀌므로 effect가 재실행돼 `toast.dismiss()`가 떠 있던 토스트를 모두 닫습니다. 같은 페이지에서 다른 이유로 리렌더돼도 `pathname`이 그대로면 실행되지 않아 토스트를 괜히 닫지 않습니다.

**왜 Layout 한 곳인가**

토스트는 단일 `<Toaster>` 큐를 공유하고 `toast.dismiss()`는 그 큐 전체를 비웁니다(2번과 같은 이유). 그래서 라우트 전환이라는 단일 길목인 Layout에 effect를 한 번만 두면, 누가 어디서 띄운 토스트든(앞으로 추가될 토스트까지) 이동 시 일괄 정리됩니다. 토스트마다, 페이지마다 닫기 코드를 넣을 필요가 없습니다. "이동하면 다 닫는다"는 전역 규칙이라 중앙 한 곳이 맞습니다.

### 세 문제를 관통하는 한 줄

1번과 3번은 전역 자원(body 스크롤, 토스트 큐)을 누군가 남긴 상태를 정리하는 문제였고, 2번은 토스트에 신원(`id`)을 부여해 중복을 흡수한 문제였습니다. 공통적으로 "전역으로 공유되는 자원을 누가, 언제, 어떻게 다루느냐"를 정확히 짚는 것이 해결의 핵심이었습니다.

## [설계 결정] 홈피드 "더보기" 기능 재설계 — 인라인 펼침 제거부터 생략 신호 단일화까지

> 분류: 설계 결정
> 맥락: 홈피드 카드의 "더보기" 기능이 빈약하고 필요성이 의심된다는 문제 제기에서 출발해, 기능을 단순화하고 본문 미리보기 생략 신호를 정리한 과정입니다. 한 번에 결론을 낸 것이 아니라, dev 서버로 눈으로 확인하며 단계마다 판단을 좁혀갔습니다.

### 출발점 — "더보기"가 정말 필요한가

기존 홈피드는 본문을 3줄로 자르고, 잘리면 "더보기" 버튼을 눌러 **카드 제자리에서 인라인으로 펼치는** 방식이었습니다. 이 기능을 그냥 삭제하고 미리보기에서 더 보고 싶으면 상세 페이지로 가게 하자는 의견이 나왔습니다.

다각도로 따져본 끝에 결정을 가른 핵심 사실은 하나였습니다. **카드 전체가 이미 상세 페이지로 가는 `<Link>`라는 점**입니다. 즉 "더 읽기" 동선이 이미 존재하는데, 인라인 펼침은 그것과 경쟁하는 두 번째 동선이었습니다. 게다가 인라인 펼침을 유지하려면 펼침 측정(`ResizeObserver`), 카드 라우팅으로 클릭이 새지 않게 막는 `preventDefault/stopPropagation`, 너비 계산 함정(과거 실제 버그 유발), 미결 상태의 임시 버튼 색까지 여러 부채를 떠안아야 했습니다. 기능 가치 대비 유지비가 컸습니다.

### 판단 기준 — 이 세션을 관통한 세 가지

조치 전체를 일관되게 끌고 간 판단 기준은 다음 세 가지였습니다.

**① 동선 중복을 제거한다.** 카드 클릭이 이미 상세로 가므로, 같은 목적의 인라인 펼침은 없앤다. "더보기"는 누르는 대상이 아니라 **더 있다는 신호**로만 남긴다.

**② 신호의 소유권을 단일화한다.** "더 있음"을 알리는 주체가 백엔드(글자수 생략)와 프론트(줄 수 클램프)로 갈리면 신호가 중복되고 불일치한다. 한쪽이 책임지게 만든다.

**③ 시각 무게는 신호에 맞춘다.** "더보기"가 버튼처럼 보이면 사용자가 그것을 정조준해야 한다고 오해하고(한손 조작 불편), 동시에 과하게 시각화되어 미니멀한 피드 톤을 깬다. 신호임이 드러나도록 무게를 낮춘다.

### 진행한 조치 — 단계별 좁혀가기

**1단계. 인라인 펼침 제거 + 신호화.** 펼침 토글·`preventDefault`·임시 색·너비 함정을 모두 걷어냈습니다. 본문은 클램프만 하고, 잘리면 "더보기"를 버튼이 아닌 텍스트로 표시합니다. 클릭은 카드 `<Link>`가 상세로 흡수합니다(별도 `onClick` 없음). 한손 도달성 우려는 여기서 해소됩니다. 누르는 대상이 작은 텍스트가 아니라 카드 전체이기 때문입니다.

**2단계. 표시 줄 수·자동 말줄임 정리.** 미리보기를 5줄까지 보여주고, 초과 시 6번째 줄에 "... 더보기"를 두기로 했습니다. 이때 CSS `line-clamp`가 잘린 5번째 줄 끝에 **자동으로 "…"를 붙이는** 동작이 6번째 줄 "... 더보기"의 "..."와 겹쳤습니다. `line-clamp`의 자동 말줄임은 `-webkit-line-clamp` 고유 동작이라 끌 수 없어, **높이 기반 클램프(`max-height` + `overflow-hidden`)로 전환**해 자동 "…" 없이 5줄에서만 자르게 했습니다.

**3단계. 백엔드 생략과의 중복 해소(신호 단일화).** 백엔드는 글자수 초과 시 `contentPreview` 끝에 "..."를 붙여 내려줍니다. 이것이 프론트 신호와 겹치는 문제를 두고 선택지를 비교했습니다.

- 백엔드에 "..."만 빼달라고 요청 → **위험.** 플래그가 없으면 5줄 이내로 짧게 잘린 글에서 프론트가 잘림 여부를 알 수 없어 "더보기"가 누락됩니다(정보 손실).
- 프론트가 백엔드 글자수 한도 이전에 미리 자름 → **취약.** 문서화되지 않은 백엔드 한도에 프론트를 묶어버려 한도 변경 시 조용히 깨집니다.
- 프론트가 백엔드 "..." 표식을 감지·제거하고 신호를 단일 소유 → **채택.** 백엔드 협조 없이 즉시 일관성을 확보합니다.

채택안은 어댑터(`utils/contentPreview.ts`)에서 끝의 "..."/"…"를 떼어내 `backendTruncated` 불리언으로 승격하고, 본문은 표식 없는 텍스트를 렌더합니다. "더보기" 노출 조건은 `backendTruncated ∥ 5줄 오버플로`로 합쳐, 글 길이와 무관하게 "... 더보기"가 일관되게 뜨고 이중 "..."가 사라집니다.

### 완결 상태 — 어디까지 끝냈나

- 세 단계 모두 dev 서버에서 시각 검증 후 develop에 반영했습니다(`fb42a22`, 그 이전 1·2단계 `bc590da`).
- **프론트 단독으로 완결**했습니다. 생략 신호의 소유권을 프론트가 갖는 상태이며, 사용자에게는 글 길이와 무관하게 일관된 "... 더보기" 하나만 보입니다.

### 남긴 한계 — 정직하게 박제

- **휴리스틱의 오탐 가능성.** "..."를 문자열로 감지하므로, 작성자가 본문을 "..."로 끝낸 짧은 글은 잘림으로 오인되어 "더보기"가 잘못 노출될 수 있습니다. 클릭해도 같은 상세로 가므로 무해하지만 부정확합니다.
- **정식 해결은 백엔드 플래그.** `contentPreview` 응답에 `contentTruncated`(또는 `hasMore`) 불리언을 추가받으면 휴리스틱을 플래그로 교체해 오탐을 제거할 수 있습니다. 또한 현재 백엔드의 생략 규칙(글자수 한도)이 openapi에 문서화되어 있지 않아, 이참에 스펙 명문화도 함께 요청 대상입니다. 백로그 `F-08 [BE]`로 기록했습니다.
- **미적용 경로.** 고민카드(`ConcernCard`)는 별도의 본문 클램프 메커니즘이라 이번 조치 범위 밖입니다. 백엔드 플래그 도입 시 동일하게 적용할지 검토 대상입니다.

### 한 줄 정리

"기능을 살릴지 말지"가 아니라 **"이 기능이 사주는 이점이 실제로 쓰이는가, 신호의 소유권은 누구에게 있어야 하는가"**를 기준 삼아, 더보기를 *경쟁 동선*에서 *단일 신호*로 축소하고 생략 권한을 프론트로 모은 과정이었습니다.

## [TIL] React Router v6+의 라우트 매칭은 작성 순서가 아니라 "구체성 랭킹"으로 정해진다

> 분류: TIL
> 맥락: 쪽지함 라우트를 등록하며 정적 경로(`/messages/new`)와 동적 경로(`/messages/:messageId`)가 같은 prefix를 공유하는 상황을 다뤘습니다. 둘의 우선순위가 어떻게 정해지는지 학습했습니다.

### 문제 상황 — 같은 prefix를 공유하는 정적/동적 경로

쪽지 기능에는 prefix가 겹치는 라우트가 세 개 있습니다.

- `/messages` — 쪽지함 목록
- `/messages/new` — 모바일 쪽지 작성 (정적 경로)
- `/messages/:messageId` — 쪽지 상세 (동적 경로)

여기서 `:messageId`는 자리 표시자라, 이론상 `new`라는 글자도 "messageId 값이 'new'다"로 받아들일 수 있습니다. 즉 `/messages/new`로 이동했을 때 작성 페이지가 아니라 상세 페이지가 `messageId='new'`로 잘못 열릴 위험이 있어 보입니다.

### 흔한 통념 — "구체적인 경로를 먼저 써라"

많은 라우팅 라이브러리(예: Express, 과거 React Router v3 등)는 **위에서 아래로 순서대로** 패턴을 검사하다 처음 맞는 것을 씁니다. 이런 모델에서는 동적 경로(`:messageId`)가 정적 경로(`new`)보다 위에 있으면 `new`까지 삼켜버리므로, **구체적인 경로를 반드시 먼저 배치**해야 합니다. 그래서 "정적 → 동적 순서로 써라"가 관용이 되었습니다.

### 실제 — React Router v6+는 순서가 아니라 랭킹으로 고른다

React Router v6부터는 매칭 방식이 바뀌었습니다. `Routes`가 자식 `Route`들을 **작성 순서와 무관하게** 한 번에 모아, 각 경로에 **구체성 점수(specificity ranking)**를 매기고 가장 점수 높은 하나를 고릅니다.

핵심 규칙은 **정적 세그먼트가 동적 세그먼트(`:param`)보다 항상 더 구체적**이라는 것입니다. 따라서:

- `/messages/new`(정적 `new`)와 `/messages/:messageId`(동적 `:messageId`)가 둘 다 있으면,
- `/messages/new`로 이동했을 때 **작성 순서가 어떻든** `new`가 더 구체적이라 항상 이깁니다.

즉 v6+에서는 두 경로의 순서를 뒤집어도 `/messages/new`가 올바르게 작성 페이지를 엽니다. "구체적인 걸 먼저 써라"는 규칙은 v6에서 **기능적으로는 더 이상 필수가 아닙니다.**

### 그래도 순서를 구체→동적으로 맞춰두는 이유

기능상 불필요해졌어도, 작성 순서를 정적 → 동적으로 두는 것은 여전히 권장됩니다. 이유는 **사람이 읽을 때**입니다. 코드를 읽는 사람은 라우터의 내부 랭킹 규칙을 매번 떠올리지 않으므로, 위에서 아래로 읽으며 "구체적인 게 먼저, 포괄적인 게 나중"이라는 직관적 순서가 유지되면 의도가 한눈에 들어옵니다. 즉 **기계를 위한 규칙이 아니라 독자를 위한 관례**로 성격이 바뀐 것입니다.

### 이중 안전망 — 잘못 매칭돼도 안전하게 떨어진다

설령 어떤 이유로 `/messages/new`가 `:messageId`로 잘못 매칭되더라도, 상세 페이지에는 `Number('new')` → `NaN`을 걸러내는 가드(`validId`)가 있어 "쪽지를 찾을 수 없어요" 화면으로 안전하게 떨어집니다. 라우팅 우선순위(1차 방어)와 컴포넌트 내부 입력 검증(2차 방어)이 겹쳐 있어, 어느 한쪽이 어긋나도 사용자에게 깨진 화면이 노출되지 않습니다.

### 한 줄 정리

React Router v6+의 라우트 매칭은 **작성 순서가 아니라 구체성 랭킹**으로 결정되며(정적 > 동적), "구체적인 경로 먼저 쓰기"는 기능적 필수에서 **가독성을 위한 관례**로 바뀌었습니다. 여기에 컴포넌트 내부 입력 가드를 더하면 라우팅 오매칭에도 안전한 이중 방어가 됩니다.
