## 🏗 설계 결정 — 고민 카드(Concern Card): 신규 게시물 타입을 설계부터 프로덕션 배포까지

**분류**: 설계 결정 / 기능 풀사이클 회고
**기간**: 2026-05-26 ~ 2026-05-29
**관련 커밋**: `8a7ac07`(설계 스펙) → `d51929b`·`2505927`·`def1c54`·`4f41d89`·`fa7deeb`(구현) → `4c3db6b`(작성/수정 + 가드) → `b1e944d`(develop→main 머지, prod 배포)

### 한 줄 요약

발달장애 아동 치료사가 임상 고민을 구조화된 카드 형태로 작성하는 신규 게시물 타입을, 백엔드 명세 협의부터 권한 설계·구현·코드리뷰·프로덕션 배포·지표 실측까지 한 사이클로 완주했습니다.

### 배경과 목표

기존 게시판은 자유 형식 글만 받았습니다. 치료사들이 "연령대·치료영역·진단명" 같은 임상 맥락을 구조화해 공유하면 동료 치료사가 비슷한 케이스를 빠르게 찾을 수 있다는 가설에서 출발한 Post-MVP 프로토타입입니다. 반응이 약하면 폐기 가능하다는 전제였기 때문에, 기존 게시물 인프라(피드·상세·댓글·리액션·스크랩)를 최대한 재사용하면서 추가 비용을 최소화하는 것이 설계 목표였습니다.

### 핵심 결정 1 — 중첩 객체 폐기, flat 아키텍처 채택

초기 설계는 `postType: 'CONCERN'`에 `concern { worry, ageGroup, diagnoses[], ... }` 중첩 객체를 두고, 프론트 뷰모델과 변환 어댑터로 격리하는 구조였습니다. 그러나 백엔드 명세(Jira MEL-55)가 확정되면서 게시물 생성/조회 계약이 일반 게시물과 1:1로 같은 flat 구조라는 점을 확인했습니다.

이 시점에서 어댑터 격리의 가치가 사라졌다고 판단해, 중첩 객체와 변환 계층을 폐기하고 게시물 타입에 `therapyArea`·`ageGroup`·`diagnoses[]`·`otherNotes` 필드를 평면으로 추가하는 방향으로 피벗했습니다. 결과적으로 작성·읽기 경로에 변환 코드가 한 줄도 들어가지 않았고, 기존 피드/상세 컴포넌트가 같은 게시물 객체를 그대로 소비합니다. `api/concerns.ts`는 변환 어댑터가 아니라 `postType`을 고정하고 기본값을 채워 일반 생성 API를 호출하는 얇은 래퍼로만 남겼습니다.

판단의 핵심은 "추상화는 미래 변경을 흡수하려고 두는 것인데, 백엔드 계약이 이미 동일 모양이면 그 추상화가 흡수할 변경이 없다"는 점이었습니다.

### 핵심 결정 2 — 권한 마스킹 (USER vs 치료사 인증)

진단명·기타 임상 메모는 민감 정보라, 인증되지 않은 USER 권한에는 백엔드가 해당 필드를 `null`로 내려보냅니다. 프론트는 `diagnoses === null`을 마스킹 신호로 해석해 본문을 숨기고 "치료사 인증 후 확인 가능" 안내로 대체합니다(`ConcernCard.tsx`). 작성 측에서도 USER 권한이 고민 카드 모드로 전환하려 하면 토스트로 막고 인증 페이지로 유도합니다(`PostWriteForm` 모드 전환 가드). staging에서 USER 토큰으로 실제 호출해 `diagnoses=null` + 블러 처리, 작성 시 백엔드 400 반환을 눈으로 확인했습니다.

### 핵심 결정 3 — 진단명 자동완성 입력 (컨트롤드 컴포넌트 + 학습 모드 구현)

`DiagnosisTagInput`은 시드 22종(한글 이름 + 영문/이칭 alias)을 기준으로 입력값을 필터링해 드롭다운 후보를 보여주고, Enter/클릭으로 태그를 추가하는 컴포넌트입니다. 세 가지를 의식적으로 설계했습니다.

- **자식이 부모 state를 직접 수정하지 않는 컨트롤드 패턴**: 부모가 `value: string[]`를 내려주고, 자식은 가드(중복·최대 10개·100자) 통과 후 `onChange(next)`로 새 배열 전체를 올려보냅니다. 가드 판정에 필요한 "현재 배열"을 props로 받기 때문에 자식만으로 검증이 닫힙니다.
- **suggestions를 useState가 아니라 매 렌더 파생값으로 계산**: useEffect+setState로 만들면 입력→렌더→effect→setState→재렌더로 한 박자 늦고 렌더가 두 번 돕니다. 컴포넌트 함수가 매 렌더 다시 실행된다는 사실에 기반해 함수 본문 변수로 충분합니다.
- **IME `isComposing` 가드**: 한글 조합 중 Enter는 조합 확정 Enter와 의도 Enter가 겹쳐 미완성 글자가 태그로 새어 들어갈 수 있어, Enter 분기에서 `nativeEvent.isComposing`을 확인합니다.

이 컴포넌트는 학습 모드로 직접 작성했고, 나머지 타입·상수·표시·배선은 AI 보조로 작성한 뒤 리뷰했습니다(작성 방법론은 별도 섹션 참고).

### 안정화 — 모달 폼 스왑에서 잡은 가드들

일반 글/고민 카드를 한 컨테이너에서 토글로 교체하는 구조라, 모달 환경에서만 드러나는 문제들을 코드리뷰(자동 다각도 리뷰 15건) 과정에서 잡았습니다.

- **폼 전환 시 입력 유실 방지**: 모드 토글이 폼 컴포넌트를 통째로 교체하므로, dirty 상태면 `confirm`으로 가드합니다.
- **중복 제출 race**: `disabled={!canSubmit}`만으로는 React 배치 안에서 두 번째 클릭이 stale 값으로 통과할 수 있어, 핸들러 첫 줄에 `if (submitting) return` 가드를 둡니다.
- **popover와 모달 backdrop 동시 닫힘**: 공개범위 popover 외부 클릭과 모달 backdrop이 같은 이벤트로 함께 닫혀 입력이 날아가는 문제를, capture 단계 리스너 + `stopPropagation`으로 React 합성 이벤트까지 차단해 해결했습니다(`VisibilityPicker.tsx`).
- **전역 모달의 모드 리셋**: 전역 모달은 닫혀도 언마운트되지 않아 마지막 모드가 부활하므로, `open` 상태를 단일 진실로 삼아 닫힐 때 모드를 초기화합니다.

### 결과

develop에서 타 직군 QA를 거친 뒤 main 머지·prod 배포까지 완료했고, GA4 실시간 보고서에서 `post_created { postType: 'CONCERN_CARD' }` 발사를 실측으로 확인했습니다. 작성·수정·권한 마스킹·자동완성이 프로덕션에서 동작합니다.

### 면접 포인트

- 추상화(어댑터)를 도입했다가 백엔드 계약 확정 후 "흡수할 변경이 없다"고 판단해 걷어낸 의사결정 과정.
- 민감 정보 권한 마스킹을 프론트/백엔드 양쪽에서 일관되게 처리한 방법(`null` 신호 해석 + 작성 가드).
- 컨트롤드 컴포넌트에서 파생값을 effect 없이 다루는 이유, IME 조합 이벤트 함정.

## 🏗 설계 결정 — 이미지 업로드 멱등성과 재시도 (presigned 3단계)

**분류**: 설계 결정 / 안정성
**기간**: 2026-05-25 ~ 2026-05-28
**관련 커밋**: `e7ea9bb`·`477b68c`(재시도 + 로깅), 백엔드 핸드오프 이슈 #11

### 한 줄 요약

presigned URL 기반 3단계 이미지 업로드(init → S3 PUT → confirm)에서, 멱등 키 계약을 백엔드와 맞추고 자동 재시도·만료 폴백·중복 확정(confirm) race를 견디는 업로드 경로를 설계했습니다.

### 배경

이미지는 init(백엔드에서 업로드 URL과 객체 키 발급) → S3에 직접 PUT → confirm(백엔드에 업로드 완료 통보) 순서로 올라갑니다. 모바일 환경에서 PUT이나 confirm이 네트워크 불안정으로 실패하면 그대로 업로드가 누락됐고, 단순 재시도를 붙이면 같은 이미지가 중복 등록될 위험이 있었습니다. 그래서 "안전하게 재시도하려면 무엇을 멱등 키로 잡아야 하는가"를 백엔드와 먼저 합의했습니다.

### 핵심 결정 1 — 멱등 키 = storedKey, init은 재시도 대상에서 제외

init이 발급하는 `storedKey`(S3 객체 경로)를 멱등 키로 삼았습니다. init을 한 번만 호출해 storedKey를 고정하면, 같은 키로 confirm이 여러 번 와도 백엔드가 멱등 처리할 수 있습니다. 따라서 **재시도 범위는 PUT/confirm으로 한정하고 init은 루프 밖에 둡니다**(`api/posts.ts`의 `uploadOneAttachment`). 멱등을 백엔드가 storedKey로 보장하므로, 프론트는 confirm 중복 재시도를 안심하고 할 수 있습니다.

### 핵심 결정 2 — storedKey 보관 위치는 재시도 방식이 결정한다

처음엔 storedKey를 ref에 보관하기로 했으나, 이는 재시도가 함수 경계를 넘는다는 가정(수동 버튼 재시도)에 기댄 것이었습니다. 자동 재시도(함수 내부 루프)로 결정하면서 storedKey는 함수 경계를 넘지 않으므로 **지역 const로 충분**하다고 정정했습니다. "어디에 상태를 두는가"가 "재시도가 어떤 경계를 넘는가"에 종속된다는 점이 핵심 학습이었습니다.

### 핵심 결정 3 — 만료 폴백: YAGNI에서 도입으로 번복

처음엔 만료(403) 폴백을 YAGNI로 배제했습니다. 정상 PUT은 수 초인데 presigned TTL은 5분이라 능동 재시도가 만료를 칠 일이 거의 없다고 봤기 때문입니다. 그러나 백엔드가 핸드오프 이슈에서 "presigned 만료 시 init 재발급"을 명시 요구했고, 폴백이 없으면 모바일 장기 단절(지하철·엘리베이터)에서 영구 실패하면서 백엔드 로그에도 흔적이 안 남는다는 점 때문에 결정을 뒤집었습니다. PUT/confirm을 두 개의 try-catch로 분리하고, PUT에서 403일 때만 init을 1회 재발급해 새 URL로 즉시 재시도하며(`reInitDone` 플래그로 1회 제한), confirm의 409 race도 같은 분리 구조 위에 한 줄로 얹는 방식(안 B)을 택했습니다.

### 검증 기법 — DevTools Request Blocking으로 S3 PUT만 차단

재시도 경로는 해피패스에선 절대 안 도는 코드라, staging(MSW off)에서 DevTools의 Request blocking으로 **S3 PUT만 강제 차단**해 검증했습니다. 두 가지 함정이 있었습니다.

- presigned URL은 매 init마다 서명 쿼리스트링과 객체 키(UUID)가 바뀌므로, 전체 URL이 아니라 **고정 버킷 호스트**만 패턴으로 잡아야 매 업로드가 계속 걸립니다.
- 최신 Chrome은 URLPattern 문법이라 `*host*` 같은 substring 와일드카드는 파싱 에러가 나고, `https://<host>/*` 형태로 줘야 합니다.

또 "마지막 시도는 throw가 console.warn보다 먼저 실행되므로 재시도 로그는 (최대 시도 − 1)회만 찍힌다"는 관찰 포인트도 정리해, 검증 시 로그 개수를 오해하지 않도록 했습니다.

### 면접 포인트

- 분산 업로드에서 멱등 키를 무엇으로 잡고 왜 init을 재시도에서 빼는가.
- 상태 보관 위치(ref vs 지역 변수)가 재시도 경계 설계에 종속된다는 점.
- YAGNI로 배제했던 만료 폴백을, 백엔드 계약과 실제 실패 모드(모바일 장기 단절)를 근거로 번복한 의사결정.
- 해피패스에서 안 도는 재시도 코드를 강제 실패 주입으로 검증하는 방법.

## 🔧 트러블슈팅 — 이미지 첨부 안정화: silent 누락 버그와 통신 실패 가시화

**분류**: 트러블슈팅
**기간**: 2026-05-23 (디코드 가드) + 2026-05-28 (로깅 컨벤션)
**관련 커밋**: `14ac498`·`026f302`(디코드 가드), `fd39c11`(통신 실패 로깅 9곳)

### 증상

모바일 삼성 브라우저에서 갤러리 사진을 첨부할 때, **에러 한 줄 없이 첨부가 0개로 누락**되는 버그가 리포트됐습니다. 미리보기 UI는 떴으나 사진이 안 보였고, 작성 완료 시에도 아무 알림이 없었습니다. 같은 환경에서 다시 첨부하면 정상이라 간헐적이었고, 데스크탑에서는 재현되지 않았습니다.

### 진단

`file.size` 메타데이터는 정상인데 **실제 바이트가 비어 있거나 덜 찬 File**이 넘어온 것으로 추정했습니다. 빈 PUT을 S3가 200으로 받아들이면 throw가 발생하지 않고, 기존 실패 카운트 기반 alert도 뜨지 않아 완전히 silent하게 새어 나가는 경로였습니다. 실물 파일은 정상 JPEG라 데스크탑 재현이 불가능했습니다.

### 조치 1 — 디코드 가드

`useFileAttachment.ts`의 파일 추가 로직을 async로 바꿔, 이미지 선택 시 `img.decode()`로 실제 렌더 가능 여부를 검증합니다. 디코드에 실패하면 대기 목록에 추가하지 않고 "이미지를 불러오지 못했어요. 다시 첨부해 주세요"로 사용자에게 즉시 알립니다. 빈/완전 깨진 File은 잡되, 부분 디코드되는 truncated 이미지는 브라우저에 따라 샐 수 있다는 한계도 함께 기록했습니다. 원인이 가설 단계라 "해결"이 아니라 "관측 가능하게 만든 뒤 재발 관측 중"으로 솔직히 남겼습니다.

### 조치 2 — 통신 실패 가시화 (로깅 컨벤션)

silent 실패의 근본 문제는 "에러를 삼키는 코드"였습니다. axios 인터셉터와 이미지 첨부 경로 9곳에 실패 로깅을 추가하면서, prefix 컨벤션을 정했습니다.

- `[api-error]` — axios 인터셉터에서 잡는 광역 통신 실패.
- `[image-attach]` — 이미지 첨부 도메인 한정 실패.

단일 실패가 광역·도메인 양쪽에 2줄로 찍히는 것은 의도된 중복으로, 인터셉터만 봐도/도메인 로그만 봐도 추적이 닫히게 했습니다. 새 도메인을 추가할 때 따를 규칙으로 박제했습니다.

### 면접 포인트

- "에러 없이 실패하는" silent 경로를 어떻게 가설로 좁혔는가(메타데이터 정상 + 빈 바이트 + S3 200).
- 재현 불가·간헐 버그를 "해결"로 단정하지 않고 관측 가능 상태로 만든 뒤 한계를 명시한 태도.
- 에러를 삼키지 않게 만드는 로깅 prefix 컨벤션 설계.

## 💡 회고 — AI 협업 코딩 방법론: 코드 소유권과 학습을 지키는 운영 체계

**분류**: TIL / 개발 방법론 회고
**기간**: 2026-05-26 ~ 2026-05-29 (지속 정착)

### 한 줄 요약

AI 보조 코딩에서 "속도"와 "내 코드 이해"가 충돌하는 문제를, 작업 유형별 분담·학습 모드·인지부채 기록이라는 세 축의 운영 규칙으로 다뤘습니다.

### 문제의식

AI에 전부 맡기면 빠르지만 내가 이해 못 한 코드가 쌓이고, 전부 직접 쓰면 느립니다. 이 프로젝트에서는 둘을 상황별로 가르는 규칙을 명시적으로 운영합니다.

### 축 1 — 작업 유형별 하이브리드 분담

- **기계적 작업**(타입 정의, 상수, 표시 컴포넌트, 배선): AI 작성 + 본인 리뷰.
- **새 로직**(폼 검증, 입력 컴포넌트의 상태 흐름): 본인 직접 작성.
- 어느 쪽이든 "왜 이렇게 동작하는가"를 본인 문장으로 재구성할 수 있어야 통과로 봅니다.

고민 카드 구현에서 타입·상수·표시·배선은 AI로 빠르게 깔고, 진단명 입력 컴포넌트는 직접 작성한 것이 이 분담의 실제 적용 사례입니다.

### 축 2 — 학습 모드: 추상에서 코드로 해상도를 올린다

새 로직을 배우며 작성할 때는 AI가 코드를 먼저 구상하지 못하게 막고, 다음 4단계로 해상도를 올립니다.

1. 화면 + 행동(무엇이 보이고 무엇이 일어나는가)
2. 데이터 모델 + 소유권(어떤 상태를 누가 소유하는가)
3. 의사코드
4. 코드

"AI가 코드를 먼저 보여주면 그 코드를 이해하는 흐름이 되어 버리는데, 그건 내가 추상에서 코드로 내려가며 설계하는 흐름과 구조가 다르다"는 문제의식에서 나온 순서입니다. 진단명 입력 컴포넌트를 이 4단계로 설계하면서, "suggestions를 왜 매 렌더 계산하는가" 같은 React 모델 규칙을 단편으로 누적했습니다.

### 축 3 — Speed Mode와 인지부채 기록

시간 압박이 있을 때는 새 로직이라도 AI 우선으로 빠르게 만들되(Speed Mode), 대신 그 코드에 **인지부채 HIGH** 태그를 붙여 별도 문서에 메커니즘·회귀 위험·자기점검 질문을 박제합니다. 다음에 그 코드를 만지기 전 그 문서로 멘탈 모델을 복원하는 것을 전제로, "지금은 빠르게, 이해는 빚으로 명시"하는 방식입니다. 고민 카드 일부 컴포넌트가 이 모드로 작성됐고, 메커니즘 7개·회귀 위험·자기점검 질문 형태로 기록을 남겼습니다.

### 회고 포인트

- AI 시대에 "내가 작성하지 않은 코드"를 어떻게 다룰지에 대한 운영 가능한 규칙.
- 속도와 학습을 이분법이 아니라 작업 유형·시간 압박으로 가른 점.
- 이해의 빚을 숨기지 않고 명시적으로 추적하는 인지부채 기록 습관.

## 🏗 설계 결정 — 쪽지(DM) 기능 설계 (구현 선행 설계 사례)

**분류**: 설계 결정 / 진행 중 설계
**기간**: 2026-05-26 ~ 2026-05-27
**관련 커밋**: `07fe646`·`8a82243`·`f532c45`(설계 스펙), `a45ab65`·`59a528e`(발송 기반·알림 타입)

### 한 줄 요약

백엔드 API가 먼저 존재하는 쪽지 기능을, 메일함 모델·푸시/풀 상태 분리·진입점 설계까지 스펙으로 확정한 사례입니다. (UI 구현은 진행 중)

### 배경

staging Swagger에 쪽지 엔드포인트(`POST /messages`, `GET /me/messages/received|sent|unread-count` 등)와 `NEW_MESSAGE` 알림 타입이 존재함을 확인하고 착수했습니다. 한 번 "API 부재"로 오확인했다가 백엔드 재확인으로 정정한 경험에서, "백엔드는 자주 바뀌니 메모리 대신 Swagger를 fresh로 다시 본다"는 절차를 굳혔습니다.

### 핵심 결정

- **메일함 모델**: 대화 스레드형이 아니라 받은함/보낸함 분리 모델로 설계했습니다.
- **상태 소유권 분리**: 안 읽음 뱃지 카운트는 store로 push 받고, 목록은 React Query로 pull합니다. 기존 알림 시스템의 구조를 그대로 미러링해 일관성을 유지했습니다.
- **진입점**: 작성자 프로필 클릭 → 드롭다운(프로필/팔로우/쪽지). 쪽지만 동작하고 프로필/팔로우는 API 부재라 "준비 중" 토스트로 UI만 둡니다. 본인 프로필이면 드롭다운을 노출하지 않습니다.
- **컴포넌트 트리거 패턴**: 작성자 아바타가 `Link` 안에 있어 네비게이션 누수를 막으려 트리거/콘텐츠 양쪽에 `stopPropagation`을 둡니다. 이 프로젝트 드롭다운은 base-ui 기반이라 Radix의 `asChild`가 없어, 트리거가 아바타를 감싸는 방식으로 구성했습니다.

### 백엔드 대기 질문 (착수 전 확인 필요)

- `NEW_MESSAGE` 알림의 `referenceId`가 messageId인가 (알림 카드 → 쪽지 상세 라우팅이 여기 의존).
- `GET /messages/{id}`가 실제 read 처리를 하는가, 어떤 조건에서 하는가 (안 읽음 뱃지 감소 로직이 여기 의존).

### 면접 포인트

- 백엔드가 먼저 있는 기능에서 추측 계약(MSW 목)으로 달리지 않고, 명세 확정 전까지 와이어/통신부를 대기시킨 판단.
- 푸시(뱃지)와 풀(목록)을 분리해 기존 알림 아키텍처와 일관되게 설계한 점.
- 라이브러리 차이(base-ui엔 `asChild` 없음)를 우회한 컴포넌트 합성 방식.
