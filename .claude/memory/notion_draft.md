## 💡 TIL — 2026-05-20 fiber, useEffect 동기화 모델, 비동기 race 도달 조건

**분류**: React 내부 동작

### 배경

리팩토링 백로그 항목(useEffect 비동기 응답 race 가드)을 점검하다가, 이 문제가 왜 발생하고 실제로 어디서 터지는지를 따라가면서 React 내부 동작까지 확장 학습했습니다.

### fiber와 reconciler 전환

fiber는 React가 컴포넌트 하나하나를 표현하기 위해 내부적으로 들고 있는 객체입니다. 컴포넌트의 state와 ref가 실제로 저장되는 곳이며, 흔히 말하는 컴포넌트 인스턴스의 실체가 이 fiber입니다.

React 16에서 reconciler를 stack 방식에서 fiber 방식으로 바꿨습니다. reconciler는 트리에서 무엇이 바뀌었는지 비교해 실제 DOM에 반영할 내용을 정하는 엔진입니다. 기존 stack 방식은 렌더를 시작하면 콜스택에 얹혀 끝까지 동기로 돌아가 중간에 멈출 수 없었고, 트리가 크면 메인 스레드를 오래 점유해 입력과 애니메이션이 끊겼습니다. fiber 방식은 작업을 fiber 단위로 쪼개고 React가 직접 관리하는 연결 리스트로 트리를 순회하기 때문에, 작업을 멈췄다가 나중에 재개할 수 있습니다. 이 중단과 재개 능력이 React 18 동시성 기능(time-slicing, Suspense, transitions)의 토대가 되었습니다.

### 리렌더는 인스턴스를 죽이지 않는다

state가 바뀌면 React는 컴포넌트 함수를 다시 호출하지만 fiber는 그대로 유지합니다. 즉 리렌더와 언마운트는 다릅니다. 리렌더는 같은 fiber에서 함수만 다시 실행해 state 값을 갱신하는 것이고, fiber가 파괴되는 것은 컴포넌트가 트리에서 제거되는 언마운트 때뿐입니다.

### StrictMode의 이중 실행

개발 모드 StrictMode는 effect를 setup, cleanup, setup 순서로 한 번 더 실행합니다. 이때 진짜 언마운트가 일어나는 것이 아니라 fiber는 그대로 두고 effect만 다시 도는 것이라서 state와 ref는 살아남습니다. 운영 환경의 동시성 기능이 state를 유지한 채 컴포넌트를 숨겼다 다시 보여줄 수 있기 때문에, 그 상황에서도 effect가 안전한지 미리 검증하려고 일부러 이렇게 동작합니다. ref 기반 가드가 이 이중 실행에서 초기화되지 않아 무한 로딩이 발생하는 버그를 이전에 겪은 적이 있는데, 그 원인이 여기서 정확히 설명됩니다.

### useEffect는 감지가 아니라 대조다

useEffect는 값을 상시 감시하는 것이 아닙니다. 매 렌더가 commit된 직후 deps 배열을 직전 렌더의 deps와 얕게(Object.is) 비교해, 달라졌을 때만 이전 effect의 cleanup을 실행하고 새 effect를 실행합니다. render는 순수해야 React가 자유롭게 호출하거나 중단할 수 있으므로, 외부 세계를 건드리는 작업(네트워크, 구독, DOM 조작)은 commit 이후 effect로 미룹니다.

감지가 아니라 대조이기 때문에 두 가지 함정이 생깁니다. 리렌더가 일어나지 않으면 deps를 비교할 기회 자체가 없어서, ref를 직접 바꾼 변화는 effect가 알아채지 못합니다. 또 비교가 얕기 때문에 객체나 배열을 deps에 리터럴로 넣으면 내용이 같아도 매 렌더마다 새 참조가 되어 매번 실행됩니다.

useEffect의 본질은 값 변화에 반응하는 것이 아니라 deps에 맞춰 외부 시스템을 동기화하는 것입니다. 그래서 유저 행동에 반응하는 로직은 이벤트 핸들러(onClick 등)에 두고, 화면에 보이는 동안 외부와 상태를 맞추는 로직만 effect에 둡니다.

### 비동기 race가 실제로 도달하는 조건

useEffect에서 fetch한 응답이 늦게 도착해 최신 화면을 덮어쓰는 race는 인스턴스 생명주기로 도달 여부가 갈립니다. 같은 인스턴스가 살아있는 채로 입력만 바뀌면 race가 가능합니다. 예를 들어 목록 필터칩은 searchParams만 바꾸므로 페이지 인스턴스가 유지되어, 칩을 빠르게 바꾸면 이전 요청 응답이 늦게 와 현재 결과를 덮어쓸 수 있습니다.

반대로 인스턴스가 언마운트되면 이전 요청의 응답이 와도 죽은 인스턴스의 setState를 React가 무시하므로 화면에 영향이 없습니다. 게시글 상세는 다른 글로 가려면 목록을 거쳐 인스턴스가 교체되기 때문에 이 경우에 해당하며, 현재 구조에서는 사실상 race가 도달하지 않습니다. 다만 fetch 요청 자체는 언마운트와 무관하게 끝까지 완료되고, 무시되는 것은 setState뿐입니다.

### 면접 포인트

- fiber가 무엇이고 stack reconciler 대비 무엇이 나아졌는가: 작업을 중단 가능한 단위로 쪼개 동시성 렌더링의 토대를 만들었습니다.
- 리렌더와 언마운트의 차이: 리렌더는 fiber 유지, 언마운트는 fiber 파괴.
- useEffect가 deps를 다루는 방식: 감시가 아니라 commit 후 얕은 대조이며, 그래서 객체 deps와 ref 직접 변경에 함정이 있습니다.
- 비동기 race를 막는 방법: AbortController로 요청을 취소하거나, cleanup에서 플래그를 세워 늦은 응답의 setState를 막습니다. React Query 같은 라이브러리는 이 처리를 내부에서 대신합니다.
