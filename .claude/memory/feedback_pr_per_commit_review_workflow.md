큰 작업(예: 시안 정합, 페이지 재설계)은 관심사를 분리해서 PR 안에 **별도 커밋**으로 올리고, 커밋이 추가될 때마다 사용자가 코드 리뷰를 진행한다. 1 PR이라도 커밋별로 리뷰 사이클을 돈다.

**Why**: (1) 로직 커밋만 머지돼도 동작은 유지되므로 부분 머지 옵션이 살아있다. (2) UI 커밋은 시각 회귀를 별도로 검증해야 한다. (3) 한 번에 큰 diff를 리뷰하면 누락 위험이 커진다. (4) 2026-05-11 CH-09 댓글 재설계에서 1/2(로직 — flatMap, props 추가) → 1차 리뷰 → 2/2(UI — 좌측 컬럼, 세로선, 꺾인 선, 타이포) → 2차 리뷰 흐름으로 운영 성공.

**How to apply**:
- 큰 UI 시안 정합/리팩토링/기능 추가 요청을 받으면 먼저 **관심사 분리 가능한지** 판단(로직 vs UI, 컴포넌트 신설 vs 기존 통합, 데이터 모델 vs 표시).
- 분리 가능하면 **2~3개 커밋 분할 안**과 **베이스 브랜치/네이밍**을 사용자에게 컨펌 후 착수. 직접 결정하지 않는다.
- 각 커밋은 단독으로 머지 가능한 안전한 상태(테스트/타입 통과, 동작 유지)여야 한다.
- 커밋 후 즉시 push해서 PR 갱신 → 사용자 리뷰 대기. **다음 커밋 진행 전에 리뷰 결과 기다린다.**
- 리뷰 OK 받으면 다음 커밋 시작, 코멘트 있으면 그 커밋 안에서 수정/롤백.
- 분리할 게 명확히 없는 작업(단일 fix, 한 줄 수정)은 굳이 분할하지 않는다.
