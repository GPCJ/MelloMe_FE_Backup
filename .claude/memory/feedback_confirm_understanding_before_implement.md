시안 캡처 첨부 + "이렇게 바꿔줘" 같은 큰 UI 변경, 또는 영향 범위 추정이 어려운 변경 요청은 코드 수정 진입 전에 "이렇게 이해했다"를 정리해서 사용자 컨펌 받은 뒤 실행해야 합니다.

**Why:** 2026-05-10 PR #12 작업 중 PDF 첨부 UI를 시안에 맞게 바꿔달라는 요청에서 사용자가 명시적으로 "너가 이해한 것을 먼저 나에게 설명하고 내가 맞게 이해했다고 판단하면 코드 수정 들어가자"고 지시했습니다. 그 흐름 그대로(이해 정리 → 컨펌 → 실행) 진행했더니 한 번에 정확한 결과물이 나왔고 사용자도 만족. 반대로 같은 세션 초반엔 worktree base 검증을 빼먹은 채 가정 기반으로 작업해서 흰 화면 등 재작업 발생.

기존 `feedback_pseudocode_first_protocol.md`(코드 의사결정 협의)나 `feedback_step_by_step_guidance.md`(작업 단계 분할)와는 다른 dimension의 protocol입니다 — **요구사항 이해의 사용자 검증** 단계를 코드 작성 직전에 두는 것.

**How to apply:**
- 트리거: 시안 캡처 첨부 + 변경 요청 / 자연어로만 표현된 큰 UI 변경 / 영향 범위 어림 어려운 작업
- 형식:
  1. 변경 항목 bullet 리스트 ("PDF 파일이 세로 1줄씩 나열", "X 아이콘 좌측", ...)
  2. "현재 vs 변경 후" 대조 (현재 96x96 카드 / 변경 후 한 줄에 ⊗ + 파일명)
  3. 불확실한 점 추가 질문 ("`1m`이 시간/크기 어느 쪽인가요?" "PDF/이미지 상하 순서는?")
  4. 사용자 OK 명시 응답 받기 ("맞아 그렇게 구현해줘")
  5. 그 후에야 코드 수정 진입
- 작은 픽셀 조정/오탈자 같은 자명 변경은 생략 가능 — 큰 구조 변경/시안 매칭에만 적용
- pseudocode-first protocol(코드 작성 의사결정)과 함께 사용 가능 — 이 메모리는 그 앞 단계(요구 이해 검증)
