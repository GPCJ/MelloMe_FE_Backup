2026-06-02 `useSendMessage.ts` 가이드 리딩으로 판명한 사용자 코드 읽기 진단.

## 핵심 발견

사용자는 **코드를 못 읽는 게 아니다.** hook 반환/구조분해 구조, 가드·setState·try/catch 흐름을 추측까지 맞추며 술술 읽음. 진짜 패턴은:

- **WHAT(이 코드가 뭘 하는지)** = 자동으로 읽힘.
- **WHY(왜 이 줄이 필요한지·어떤 사고를 막는지)** = 기본값으로 건너뜀. 가드 줄을 "가드 로직이네" 분류만 하고 다음 줄로 통과시키는 패턴 2회 관찰. 콕 집어 물으면 정확히 답함 → 능력이 아니라 **습관** 문제.

[[user_dev_style]]의 "기능 구현 강, 설계 약 자각"과 정확히 같은 지점. WHAT은 눈에 보이니 읽히고, WHY(방어/설계 의도)는 안 보이니 통과.

## "코드 리뷰 부담"의 정체

큰 PR 읽기 부담의 정체 = ① 분량(착시 — GUI diff가 실제보다 부풀려 보임. 막상 읽으면 안 어려움) + ② "전 줄 WHY까지 짚으려니 무겁다"는 부담. [[user_ai_dependency_anxiety]]의 "AI 없이 못 읽/못 짤까봐" 불안이 이 형태로 재출현했고, 한 파일 가이드 리딩(테스트 가능한 실험)으로 끊어냄.

## How to apply

- 가이드 리딩/리뷰 시 사용자의 WHAT 답에서 멈추지 말고, **risk 줄(가드·에러분기·옵셔널 체이닝 등)에서만 "이거 지우면 뭐 깨지지?"**로 WHY를 한 번 더 콕. JSX·보일러플레이트는 훑기 허용.
- 분량 공포·"다 못 읽겠다" 호소 시: "착시 + WHY는 risk 줄에만"으로 리프레임. 전 줄 동일 강도 정독은 실무 프로도 안 함을 상기.
- 프로페셔널 정체성 불안과 엮여 나오면 [[user_ai_dependency_anxiety]] 4프레임, 특히 "테스트 가능한 실험(한 파일 같이 읽기)"으로 redirect.
- 코드 리뷰 진행 방식 자체는 [[feedback_ai_response_latency_focus]] 참조(본인 self-read + 의문만 배치 질문).
