노션 작성/업로드 관련 합의 규칙 모음입니다.

---

## 1. 업로드 워크플로우 — 초안 확인 + 경로 안내

1. **업로드 전**: 채팅창에 초안 먼저 보여주고 사용자 승인 후 업로드
2. **업로드 후**: 상속 경로로 안내 (예: "빌더스 리그 > TIL > 2026-03-27 — 제목")

**Why:** Claude 작성 내용이 실제와 다를 수 있고, 링크만으론 어떤 섹션에 작성됐는지 알 수 없음.

**How to apply:** `/update-notion`, `/update-builders`, `/update-til` 등 모든 Notion 업로드 작업에 적용.

---

## 2. 날짜별 페이지 방식

매일 작성하는 노션 페이지(TIL, 진행 상황 등)는 날짜별로 **서브페이지를 생성**해서 구분합니다. 메인 페이지에 직접 내용 추가 X.

**Why:** 토글 방식보다 페이지 방식이 내용 많아질수록 깔끔하고, 페이지 단위 공유/링크 가능.

**How to apply:** `/update-til`, `/update-builders` 등 날짜별 기록 작성 시 메인에 직접 추가하지 말고 해당 날짜 제목의 서브페이지 생성.

---

## 3. 항목 번호는 fetch로 실제 확인 후 결정

노션에 순번 있는 항목(트러블슈팅 번호 등) 추가 전, 메모리에 기록된 번호를 그대로 쓰지 말고 반드시 `notion-fetch`로 실제 페이지 확인 후 번호 결정.

**Why:** 메모리는 #004까지로 기록됐으나 실제는 #006까지 있었음. #005로 작성하려다 사용자가 직접 잡아줘야 했음. 메모리는 언제나 stale 가능.

**How to apply:** 순번 항목 추가 시 `notion-fetch` → 현재 상태 확인 → 다음 번호 결정.

---

## 4. 서브페이지 분리 전 양질 자기평가

작업을 노션 서브페이지로 분리할지 결정하기 전에 **"독립 서브페이지 1개 가치의 어필 포인트인가"** 비판적으로 자기평가. 내용 대비 과포장된 구조는 면접 신뢰도를 떨어뜨림.

**Why:**
- 작은 리팩토링/기초 개념을 "SOLID 이해합니다" 식 장문으로 늘리면 미숙해 보임
- 여러 주제를 하루 단위로 엮으면 "증상 → 재진단 → 증거 기반 협업 → 판단 근거" 같은 엔지니어링 성숙도 스토리가 드러나 면접 재료로 더 강함
- 2026-04-21 트러블슈팅/TIL/설계결정 3분할 제안 → 사용자가 "내용 대비 포장 과함" 지적 → TIL 1개 통합으로 재구성 → 더 강한 스토리

**How to apply:**
- 다분할 제안 전 각 후보가 "홀로 서 있을 양인가" 자문 (코드 변경 규모 / 개념 난이도 / 본인 판단·기여)
- 약하면 하루/주제 단위 TIL 1개에 통합, 핵심 섹션은 "콜아웃 박스"로 돌출
- 사용자에게도 정직하게 판단 공유 ("솔직히 분리는 과포장, 통합 권장")

## 5. pull-mello 후 노션 초안 존재 시 VSCode 우선 확인

`pull-mello` 실행 후 `.claude/memory/notion_draft.md`에 업로드 대기 내용이 존재하면, **다른 작업보다 1순위로** `code .claude/memory/notion_draft.md`로 VSCode를 열어 "초안이 남아있습니다, 확인해주세요" 요청.

**Why:** 내용이 풍부한 초안은 집중력 좋을 때 업로드하고 싶어서, 세션 시작 시점에 바로 상기시켜주는 것을 원함.

**How to apply:** pull-mello 완료 직후 notion_draft.md 프론트매터 이후 실제 내용(#으로 시작하는 섹션) 존재 확인 → 있으면 즉시 VSCode로 열고 알림.

## 6. /report-notion 재질문 기준

재질문은 **날짜/분류/임팩트 3가지만**. 기술 디테일은 소스코드에서 직접 채울 것.

**Why:** 매일 노션 기록이 목표인데 재질문 부담 크면 기록 안 하게 됨. 사용자가 심도 검수 안 해도 수준 높은 초안이 나와야 함.

**How to apply:**
- ✅ 물어도 되는 것: 날짜/시점(git log 추정 불가) / 페이지 분류(TIL vs 트러블슈팅 구분 불가) / 결과·임팩트가 코드·메모리 어디에도 없을 때
- ❌ 절대 묻지 않는 것: 기술 디테일, 패턴명, API명, 구현 방법 → 소스코드 직접 읽어서 채움
- 탐색 순서: pull-mello → 메모리 파일 → git log → 소스코드 → 그래도 없으면 질문
